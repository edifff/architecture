# Лабораторная работа: групповой чат на PostgreSQL и jOOQ

Проект реализует групповой чат. Логика чата доступна как напрямую через Java API в
одном процессе, так и по сети: встроенный сервер Jetty принимает запросы сервлетами,
а клиент общается по протоколу HTTP. Состояние хранится в PostgreSQL, доступ к
которому идёт через типизированный API jOOQ.

## Требования и запуск

- JDK 25;
- Maven 3.9+;
- Docker (для кодогенерации jOOQ и тестов через Testcontainers).

```shell
mvn test
```

Во время сборки плагин `testcontainers-jooq-codegen-maven-plugin`:

1. поднимает временный контейнер `postgres:15-alpine`;
2. применяет миграции Flyway из `src/main/resources/db/migration`;
3. генерирует метамодель jOOQ из живой схемы в `target/generated-sources/jooq`
   (пакет `ru.archlabs.chat.db`).

Тесты, в свою очередь, поднимают собственный контейнер `postgres:16-alpine` через
Testcontainers и работают с настоящей базой.

Файл `.mvn/jvm.config` задаёт `-Dapi.version=1.40`, а конфигурация surefire —
одноимённое системное свойство (плюс такой же запасной вариант в тесте для запуска
из IDE). Это обходит известное ограничение старого docker-java внутри Testcontainers:
без него клиент использует Docker API 1.32, который отклоняют современные движки
Docker (требуется версия не ниже 1.40). Сгенерированные классы jOOQ в репозитории
не хранятся — они создаются заново при каждой сборке.

## Использование

Хранилище открывает соединение, применяет миграции Flyway и создаёт jOOQ-контекст:

```java
var storage = new PostgresChatStorage(
        "jdbc:postgresql://localhost:5432/chat", "chat", "chat");
ChatServer server = new ChatServerImpl(storage);
```

Клиент подключается через `ChatSession`:

```java
var inbox = new ArrayList<Message>();

try (var ivan = server.connect("ivan", inbox::add)) {
    ivan.send("Привет!");
    ivan.setNotificationsEnabled(false);
    List<Message> history = ivan.history();
}

server.close();
```

Сообщение доставляется всем подключённым пользователям с включёнными уведомлениями,
включая отправителя. Пользователям, которые в этот момент были offline, оповещение
сохраняется в базе и выдаётся при следующем подключении — в том числе после аварийного
завершения процесса. Историю можно запросить после отключения уведомлений. Повторное
одновременное подключение одного имени запрещено.

## Структура

- `ChatServer` — интерфейс сервера чата;
- `ChatServerImpl` — потокобезопасная реализация координации сессий и доставки;
- `ChatApplication` — точка входа процесса (читает настройки из переменных окружения);
- `ChatSession` — интерфейс клиентской сессии (метод `send` возвращает `Message`);
- `ChatStorage` — интерфейс хранилища состояния;
- `PostgresChatStorage` — хранилище на PostgreSQL, построенное на jOOQ;
- `ru.archlabs.chat.http` — сетевой слой: `ChatHttpServer` (встроенный Jetty и
  сервлеты), `HttpChatClient`/`HttpChatSession` (HTTP-клиент), `ChatProtocol` и
  `ChatJson` (описание JSON-протокола), `MetricsServlet` (`GET /metrics`);
- `ChatMetrics` — счётчики Prometheus (запросы и доставленные оповещения);
- `db.migration/V1__init.sql` — миграция Flyway со схемой `users` и `messages`;
- `db.migration/V2__notifications.sql` — миграция Flyway с очередью недоставленных
  оповещений `notifications`;
- `ru.archlabs.chat.db` — сгенерированные jOOQ-классы (в `target/`);
- `ChatServerContractTest` — общий контракт, который выполняется и напрямую, и по HTTP;
- `PostgresChatServerTest` — прямой вариант контракта и проверка перезапуска;
- `HttpChatServerTest` — тот же контракт по сети;
- `HttpChatProtocolTest` — тесты HTTP-протокола и доставки SSE;
- `Dockerfile` — образ чат-сервера;
- `compose.yaml` — PostgreSQL (с томом для данных), чат-сервер и контейнер тестов.

## Сетевой протокол (HTTP + Jetty)

Серверная часть — встроенный Jetty 12 (`ChatHttpServer`) с сервлетами по спецификации
Jakarta Servlet 6.0. Клиентская часть — `HttpChatClient`, реализующий интерфейс
`ChatServer`, и `HttpChatSession`, реализующий `ChatSession`. Благодаря этому
прикладной код не зависит от транспорта, а общий контракт (`ChatServerContractTest`)
выполняется и для прямой, и для сетевой реализации.

Транспорт — HTTP/1.1, тело запросов и ответов — JSON (библиотека Jackson).

### Как клиент вызывает функции сервера

| Функция | HTTP-запрос | Тело | Успех | Ошибки |
| --- | --- | --- | --- | --- |
| подключиться | `POST /sessions/{username}` | — | `201` | `400`, `409` |
| отключиться | `DELETE /sessions/{username}` | — | `204` | `404` |
| состояние | `GET /users/{username}` | — | `200` `User` | `404` |
| отправить | `POST /messages/{username}` | `{"text": "..."}` | `201` `Message` | `400`, `409` |
| история | `GET /messages/{username}` | — | `200` `[Message]` | `409` |
| уведомления | `PUT /notifications/{username}` | `{"enabled": true|false}` | `204` | `409` |
| оповещения | `GET /events/{username}` | — | `200` SSE | `404` |
| метрики | `GET /metrics` | — | `200` text | — |

Сообщение в JSON: `{"id": 1, "sender": "ivan", "text": "hello", "sentAt": "2026-...Z"}`,
состояние пользователя: `{"name": "ivan", "online": true, "lastConnected": "...", "notificationsEnabled": true}`.

Коды ошибок: `400` — пустые имя или текст, `404` — неизвестный пользователь, `409` —
конфликт состояния (повторное подключение, отправка из неактивной сессии, запрос
истории при включённых уведомлениях). Тело ошибки — `{"error": "..."}`.

`HttpChatClient` преобразует коды обратно в доменные исключения (`409` →
`IllegalStateException`, `400`/`404` → `IllegalArgumentException`), поэтому контракт
чата не меняется при переходе на сеть.

### Как доставляются оповещения

Оповещения доставляются по **Server-Sent Events**: клиент держит открытым поток
`GET /events/{username}` с типом `text/event-stream`. На сервере для каждого
подключённого HTTP-клиента создаётся очередь сообщений (`ClientConnection`). Доменный
`ChatServer` при отправке вызывает обработчик этой очереди, а SSE-сервлет
(`EventsServlet`) вычитывает очередь и записывает события:

```text
event: message
data: {"id":1,"sender":"andray","text":"hi","sentAt":"2026-..."}
```

Если новых сообщений нет, сервер периодически отправляет комментарий-keep-alive,
чтобы соединение не закрылось по таймауту. Клиентский `HttpChatSession` читает поток в
отдельном потоке и на каждое событие вызывает переданный обработчик `onMessage`.

### Как оповещения переживают аварийное завершение

Очередь `ClientConnection.pending` живёт в памяти и при аварийном завершении процесса
теряется. Чтобы этого не происходило, оповещения для отсутствующих пользователей
хранятся в PostgreSQL, в таблице `notifications` (миграция `V2__notifications.sql`):

- при `ChatServerImpl.send` в **одной транзакции** с сообщением создаются строки
  `notifications(recipient, message_id, created_at)` для всех offline-пользователей с
  включёнными уведомлениями (`INSERT ... SELECT FROM users WHERE online = FALSE AND
  notifications_enabled = TRUE`);
- онлайн-пользователи (включая отправителя) получают оповещение сразу через SSE, без
  записи в таблицу;
- при подключении `ChatServerImpl.connect` под блокировкой выбирает
  `ChatStorage.undeliveredNotifications`, затем отдаёт сообщения обработчику в порядке
  идентификаторов и удаляет доставленные строки (`clearNotifications`).

Так пользователь, который был не подключён на момент нештатного завершения работы,
после рестарта снова подключается и получает все накопленные оповещения: строки лежат в
базе и не зависят от памяти процесса. При старте `PostgresChatStorage` сбрасывает
`online` в `FALSE`, поэтому после рестарта прежние сессии не считаются активными.

### Как собираются метрики (Prometheus)

Метрики считает официальный Prometheus Java-клиент (`prometheus-metrics-core`) в классе
`ChatMetrics`. У каждого экземпляра собственный `PrometheusRegistry`, поэтому счётчики
разных серверов не смешиваются. Значения отдаются на `GET /metrics` сервлетом
`MetricsServlet` в текстовом формате Prometheus:

```text
# HELP chat_requests_total Processed user requests
# TYPE chat_requests_total counter
chat_requests_total{operation="connect"} 2.0
chat_requests_total{operation="send"} 1.0
# HELP chat_notifications_total Notifications delivered to users
# TYPE chat_notifications_total counter
chat_notifications_total{channel="live"} 2.0
chat_notifications_total{channel="backlog"} 1.0
```

- `chat_requests_total{operation}` — счётчик обработанных пользовательских запросов:
  `connect`, `disconnect`, `user`, `send`, `set_notifications`, `history`;
- `chat_notifications_total{channel}` — счётчик доставленных пользователям оповещений:
  `live` (онлайн-доставка) и `backlog` (накопленные оповещения, выданные при подключении).

`ChatHttpServer` получает тот же экземпляр `ChatMetrics` у серверной логики (интерфейс
`ChatMetrics.Source`, который реализует `ChatServerImpl`) и вешает сервлет на путь
`/metrics`. Скрейп Prometheus настраивается стандартно:

```yaml
scrape_configs:
  - job_name: chat
    static_configs:
      - targets: ["localhost:8080"]
```

## Запуск в контейнерах Docker

Приложение упаковано в контейнеры: PostgreSQL и чат-сервер работают как отдельные
сервисы `compose.yaml`, а тесты выполняются в третьем, отдельном контейнере.

### Точка входа и настройка

`ChatApplication` — точка входа процесса. Параметры берутся из переменных окружения,
поэтому образ не зависит от окружения:

| Переменная | Назначение | Значение по умолчанию |
| --- | --- | --- |
| `CHAT_DB_URL` | JDBC-адрес PostgreSQL | `jdbc:postgresql://localhost:5432/chat` |
| `CHAT_DB_USER` | пользователь БД | `chat` |
| `CHAT_DB_PASSWORD` | пароль БД | `chat` |
| `CHAT_HTTP_PORT` | порт HTTP-сервера | `8080` |

При старте приложение ждёт готовности PostgreSQL (до 30 попыток), применяет миграции
Flyway и поднимает Jetty. По `SIGTERM` срабатывает обработчик завершения: Jetty
останавливается, активные сессии закрываются, соединение с базой освобождается —
поэтому выключение и повторный запуск контейнера не оставляют висящих `online`-сессий.
Исполняемый jar (`target/chat.jar`) собирается плагином `maven-shade-plugin`.

### Сборка и запуск

Во время `mvn package` плагин jOOQ поднимает временный контейнер PostgreSQL через
Testcontainers, поэтому сборка требует доступа к Docker-демону. Внутри `docker build`
демон недоступен, поэтому jar собирается заранее — из IDE либо сервисом `builder`,
которому проброшен `/var/run/docker.sock`:

```shell
# 1. Собрать target/chat.jar (JDK 25 + Docker)
docker compose --profile build run --rm builder

# 2. Собрать образ и поднять PostgreSQL + чат-сервер
docker compose up --build -d

# 3. Проверить работу
curl http://localhost:8080/metrics
```

`Dockerfile` собирает образ на базе `eclipse-temurin:25-jre`, копирует `target/chat.jar`
и запускает его. Сервис `chat` подключается к сервису `db` по имени
`jdbc:postgresql://db:5432/chat` — так контейнеры взаимодействуют внутри одной сети
compose. Для отладки порт PostgreSQL проброшен на хост как `5433` (внутри сети он
по-прежнему `5432`).

### Как состояние переживает перезапуск

Данные PostgreSQL лежат в именованном томе `chat-db-data`
(`/var/lib/postgresql/data` внутри контейнера). Том не удаляется при
`docker compose stop`, `restart` или `down`, поэтому пользователи, сообщения и
недоставленные оповещения сохраняются. Перезапуск можно проверить так:

```shell
docker compose restart chat      # или: docker compose stop && docker compose start
curl http://localhost:8080/users/ivan   # история и настройки на месте
```

Том удаляется только явно: `docker compose down -v`.

### Тесты внутри Docker и из IDE

Тесты используют Testcontainers, поэтому им тоже нужен Docker-демон. Оба сценария
запускают один и тот же набор тестов:

```shell
# Внутри Docker — отдельным контейнером (Docker-сокет проброшен)
docker compose --profile test run --rm tests

# Из ИСР — обычный запуск JUnit или Maven (Docker используется Testcontainers)
mvn test
```

В контейнере тестов переменная `TESTCONTAINERS_HOST_OVERRIDE=host.docker.internal`
и запись `host.docker.internal:host-gateway` позволяют клиенту внутри контейнера
подключаться к проброшенным портам контейнера PostgreSQL, который запускает
Testcontainers. Сервисам `builder` и `tests` проброшен `/var/run/docker.sock`, а
`group_add` добавляет контейнерному пользователю группу сокета (`DOCKER_GID`, по
умолчанию `1001`); при другом значении задайте его перед запуском:
`DOCKER_GID=$(stat -c '%g' /var/run/docker.sock) docker compose --profile test run --rm tests`.

## Контрольные вопросы

### Как устроено сетевое взаимодействие?

Сервер поднимает встроенный Jetty с сервлетами, а клиент вызывает функции сервера
обычными HTTP-запросами и получает оповещения по Server-Sent Events (подробности — в
разделе «Сетевой протокол»). Поскольку `HttpChatClient` реализует интерфейс
`ChatServer`, а `HttpChatSession` — `ChatSession`, вызывающий код не зависит от того,
работает ли чат в одном процессе или по сети. Отдельный набор тестов
`HttpChatProtocolTest` проверяет коды ответов, формат JSON и доставку событий SSE, а
общий `ChatServerContractTest` прогоняет один и тот же сценарий и по HTTP.

### Как имитируется одновременная работа разных клиентов?

В приложении каждый клиент представлен объектом `ChatSession`, а в тесте
`ChatServerContractTest.concurrentClientsDoNotLoseMessages` клиенты запускаются в
разных потоках (сценарий выполняется и для прямой, и для сетевой реализации):

1. `Executors.newFixedThreadPool(2)` создаёт два рабочих потока.
2. Через `submit` в них запускаются задачи клиентов `ivan` и `andray`.
3. Каждый клиент самостоятельно подключается к одному экземпляру `ChatServer`.
4. `CyclicBarrier(2)` задерживает оба потока до готовности и затем одновременно
   разрешает им отправлять сообщения.
5. Каждый клиент отправляет по 100 сообщений.
6. Вызовы `Future.get(5, TimeUnit.SECONDS)` ожидают завершения задач, передают в
   тест исключения из клиентских потоков и не позволяют тесту зависнуть навсегда.

После завершения потоков тест проверяет, что в истории находятся все 200 сообщений,
их идентификаторы идут без пропусков от 1 до 200, а от каждого отправителя сохранено
ровно по 100 сообщений. Значит, тест проверяет не просто запуск нескольких потоков,
но и отсутствие потерь данных при их конкуренции.

Потокобезопасность реализована в `ChatServerImpl`: операции подключения, отправки,
изменения настроек, чтения истории и отключения защищены `synchronized (this)`.
Поэтому общая карта активных сессий и обращения к хранилищу выполняются
последовательно. Обработчики доставки вызываются уже после выхода из
синхронизированного блока, чтобы медленный или ошибочный клиент не удерживал
блокировку сервера.

### Как jOOQ используется для доступа к данным?

Вместо ручного JDBC с `PreparedStatement` и разбором `ResultSet` запросы описываются
типизированным DSL jOOQ. Метамодель (`Users`, `Messages`, их поля и записи)
генерируется плагином `testcontainers-jooq-codegen-maven-plugin` прямо из живой схемы
PostgreSQL, поэтому имена таблиц и столбцов проверяются компилятором.

Примеры соответствия:

- `SELECT ... FROM users WHERE name = ?` → `dsl.selectFrom(USERS).where(USERS.NAME.eq(name))`;
- `INSERT ... RETURNING id` → `dsl.insertInto(MESSAGES)...returning(MESSAGES.ID).fetchOne()`;
- `UPDATE users SET online = ?` → `dsl.update(USERS).set(USERS.ONLINE, value)...`.

Схема создаётся миграцией Flyway `V1__init.sql`. Так как источник метамодели —
реальная база, код и структура таблиц не могут разойтись незаметно: при изменении
миграции следующий `mvn generate-sources` перегенерирует классы, и несовместимость
проявится при компиляции.

### Как сохраняется состояние после перезапуска?

Состояние записано в три таблицы PostgreSQL:

- `users`: имя, признак подключения, время последнего подключения и настройка
  уведомлений;
- `messages`: идентификатор, отправитель, текст и время отправки;
- `notifications`: недоставленные оповещения offline-пользователей (получатель,
  сообщение, время создания).

Интерфейс `ChatStorage` отделяет логику чата от способа хранения: `ChatServer` и
`ChatSession` не зависят от конкретной реализации. При повторном запуске создаётся
новый `PostgresChatStorage` с тем же JDBC URL. Flyway видит, что миграция уже
применена, и не меняет схему, после чего запросы `user()` и `history()` читают уже
записанные строки.

Признак `online` намеренно сбрасывается в `FALSE` методом `resetOnlineUsers()`: после
перезапуска прежних клиентских потоков и объектов `ChatSession` больше нет,
следовательно, считать таких пользователей подключёнными было бы неверно.

Штатный сценарий проверяет `PostgresChatServerTest.restoresStateAfterRestart`:
первый сервер закрывается, второй открывает ту же базу и получает сохранённое
состояние — историю, настройку уведомлений и время последнего подключения.

### Как обеспечивается согласованность изменений?

Каждая изменяющая операция `PostgresChatStorage` — подключение, отключение,
изменение настроек и добавление сообщения — выполняется через общий метод
`transaction()`:

1. отключается автоматическое подтверждение (`setAutoCommit(false)`);
2. весь набор jOOQ-запросов операции выполняется на одном соединении;
3. при успехе вызывается `commit()`;
4. при `DataAccessException` (ошибка SQL) или другом исключении времени выполнения
   вызывается `rollback()`;
5. режим автоматического подтверждения восстанавливается.

Таким образом, операция сохраняется целиком либо не сохраняется вообще. Ошибки jOOQ
преобразуются в `StorageException`, а осмысленные нарушения (повторное подключение,
неизвестный пользователь) остаются `IllegalStateException` и `IllegalArgumentException`.
В схеме заданы первичный и внешний ключи и ограничения `NOT NULL`, которые не дают
записать внутренне противоречивые данные.

### На что влияет сохранение состояния в хранилище?

Сохранение состояния влияет на следующие свойства программы:

- **Надёжность.** Пользователи, их настройки и сообщения переживают перезапуск
  процесса. Незавершённые изменения не оставляют частично обновлённое состояние.
- **Производительность.** Вместо изменения коллекций в памяти выполняются SQL,
  сетевой обмен с СУБД и `commit`. При этом типизированный DSL jOOQ и генерация кода
  убирают ручной разбор `ResultSet` и уменьшают число ошибок.
- **Параллельная работа.** В этой реализации `ChatServerImpl` последовательно
  выполняет обращения к одному JDBC-соединению под своей блокировкой. Это делает
  доступ корректным для нескольких клиентских потоков, но ограничивает пропускную
  способность одним изменением состояния за раз.
- **Модель данных.** Появляются таблицы, типы столбцов, ключи и ограничения, а также
  метамодель jOOQ, которые нужно поддерживать при дальнейшем изменении приложения.
- **Обработка ошибок и жизненный цикл.** Ошибки jOOQ преобразуются в `StorageException`,
  неуспешные транзакции откатываются, а соединение требуется закрывать.
- **Тестирование.** Тесты используют Testcontainers и проверяют поведение на том же
  PostgreSQL, что и рабочая среда, вместо встроенной in-memory СУБД.

Публичный Java API чата от способа хранения не зависит: клиент по-прежнему работает
через `ChatServer` и `ChatSession`.

### Какие метрики собираются и как их получить?

Собираются две величины: число обработанных пользовательских запросов
(`chat_requests_total{operation}`) и число доставленных пользователям оповещений
(`chat_notifications_total{channel}`). Обе — счётчики (`counter`): они только
увеличиваются, а Prometheus вычисляет по ним скорость через `rate()`. Счётчики ведёт
`ChatMetrics`, значения отдаются на `GET /metrics` в текстовом формате Prometheus
(подробности — в разделе «Как собираются метрики»). Метки `operation` и `channel`
позволяют разложить общее число по видам операций и по способу доставки (`live`/`backlog`),
а не видеть только итог.

### Как гарантируется доставка оповещений при аварийном завершении?

Оповещения для offline-пользователей не держатся в памяти, а пишутся в таблицу
`notifications` в одной транзакции с сообщением. При аварии процесса строки остаются в
PostgreSQL; после перезапуска `PostgresChatStorage` сбрасывает признак `online`, и при
следующем подключении `ChatServerImpl.connect` выбирает недоставленные оповещения,
отдаёт их пользователю по порядку и удаляет. Онлайн-пользователи получают оповещение
сразу, поэтому в таблицу для них ничего не пишется. Так требование «пользователи, не
подключённые на момент нештатного завершения, должны получить свои оповещения»
выполняется за счёт персистентной очереди на стороне хранилища (подробности — в разделе
«Как оповещения переживают аварийное завершение»).
