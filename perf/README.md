# Замеры производительности при масштабировании

Лабораторная работа: слоистая архитектура. Каждый слой — отдельный контейнер,
взаимодействие только по gRPC/protobuf:

```
api (Facade, библиотека)  →  chat (домен)  →  storage (хранение)  →  db
```

## Что и как измеряется

- **Нагрузка:** k6 с нативным gRPC (`perf/k6/chat.js`, `perf/k6/storage.js`).
  Каждый VU держит один канал и работает со своим набором пользователей.
- **Масштабирование:** `docker compose --scale <layer>=N` (1 → 2 → 4 реплики),
  фиксированные host-порты снимаются override-файлом `perf/compose.scale.yaml`.
- **Session affinity:** при N репликах VU привязывается к конкретной реплике
  (`arch-labs-chat-K`), иначе `Connect` и последующие вызовы одного пользователя
  попали бы в разные процессы.
- **Чистое состояние:** перед каждым прогоном таблицы очищаются, иначе `History`
  возвращает всё больше строк и латентность растёт от прогона к прогону.
- **Метрики:** каждый слой отдаёт `/metrics` (Prometheus), Grafana — дашборд
  `perf/grafana/dashboards/arch-labs.json` (RPS, p95, ошибки по слоям).

## Запуск

```bash
docker compose up -d --build          # db + storage + chat + prometheus + grafana
perf/scale.sh chat 30 15s              # матрица для доменного слоя
perf/scale.sh storage 30 15s           # матрица для слоя хранения
```

Результаты: `perf/results-chat.csv`, `perf/results-storage.csv`.
Grafana: <http://localhost:3000> (анонимный доступ), Prometheus: <http://localhost:9090>.

## Колонки CSV

| Колонка | Значение |
|---|---|
| `iterations` | завершённые итерации сценария |
| `rps` | итераций в секунду |
| `avg_ms`, `p50_ms`, `p95_ms`, `p99_ms` | латентность gRPC-вызовов |

## Интерпретация

Ожидаемая картина для этой архитектуры:

- `chat` масштабируется до тех пор, пока не упрётся в **единственный**
  `storage`-сервис: у него одно JDBC-соединение, и все операции сериализуются.
  Поэтому 4 реплики `chat` могут быть медленнее 2 — это не ошибка замера, а
  обнаруженное узкое место слоя хранения.
- `storage` масштабируется, пока не упрётся в PostgreSQL: каждая реплика держит
  собственное соединение, запись идёт в одни и те же таблицы.

Это и есть цель работы: показать, что масштабирование слоя помогает только до
границы следующего слоя.
